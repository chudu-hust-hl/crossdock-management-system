# Domain Model

This document records the agreed domain design for `cross-dock-management`. It is the source of truth for collections, identifiers, relationships, and naming. Changing anything here requires explicit approval.

Field names written in `code` style are agreed. Fields described in plain words are agreed in meaning, but their exact name or type is decided when the schema is implemented (see [Open questions](#open-questions)).

Field-level types, defaults, indexes, and validation are in [`schema-design.md`](./schema-design.md). Processes that span several collections (Location reuse, shipment creation, routing) are in [`business-workflows.md`](./business-workflows.md). How a scan, a missing item, a manual pickup, or a manual delivery changes Item, DockTask, Route, and Shipment status is in [`scanning-flows.md`](./scanning-flows.md). That flow is agreed and not implemented.

## 1. Collections

The initial domain collections are:

| Collection | Represents | NestJS module |
| --- | --- | --- |
| `locations` | Warehouses, cross-docks, stores, customer locations | `locations` |
| `users` | System users and their roles | `users` |
| `items` | Physical items moving through the network | `items` |
| `shipments` | Overall shipments **and** shipment segments | `shipments` |
| `routes` | Operational routes with embedded stops | `routes` |
| `dock_tasks` | One operational action on one item | `dock-tasks` |

Supporting collection: `metadata` (module `metadata`), a small store of values and rules that may change, identified by `scope` + `key` (open question 16). It is implemented for the monthly business-code counters; routing data (postal-code ranges, distances) is planned to use it later. Fields are in [`schema-design.md` §11](./schema-design.md#11-metadata).

Do **not** introduce new collections such as `warehouses`, `shipment_legs`, `route_stops`, or `operations` without an explicit requirement and approval.

## 2. Identifiers

Every persisted domain entity has two identifiers:

| Field | Type | Purpose |
| --- | --- | --- |
| `id` | ULID string, unique index | **The identifier the application uses everywhere**: in references between documents, in lookups, and in the API |
| `_id` | MongoDB `ObjectId` | MongoDB's own primary key. Kept because MongoDB requires one, but not used by the application |

Example ULID: `01M4GVJ9TMCR0DTRTXG3JHTPHS`.

Rules:

- **References between documents store the target's ULID `id`** as a string, for example `parentId`, `itemIds`, `deliveryInfos[].locationId`, `stops[].locationId`, `itemId`, `inboundLegId`, `createdBy`, and `performedBy`. They never store an `_id` ObjectId.
- A reference is resolved by looking up the target by `id` (`findOne({ id })`), which uses the unique `id` index. Mongoose `populate` is not used, because it only follows `_id`.
- Public APIs send and receive the same ULIDs that are stored, so no ULID ↔ ObjectId conversion exists anywhere.
- ULIDs are stored and compared in their canonical upper-case form. A lower-case ULID is rejected, because references are matched as exact strings.
- Do not replace `_id` with a ULID. It stays as MongoDB's default primary key.
- ULIDs are generated by one shared utility based on the `ulid` package. Modules must not implement their own generation logic.
- Every domain schema has a unique index on `id`.

## 3. Shared conventions

### Time

- Planned windows: `appointment: { from, to }`.
- Actual windows: `actualWindow: { from, to }`.
- Persisted dates are JavaScript `Date` values in UTC.
- Every domain entity has `createdAt` and `updatedAt` (Mongoose timestamps).
- Do not replace the grouped windows with separate fields such as `plannedStartAt`, `plannedEndAt`, `actualStartAt`, or `actualEndAt` without explicit approval.

### Soft delete

Every collection uses soft delete. Documents are never removed from MongoDB, with one exception: when a booking fails, the booking's own new Items and new stores are hard-deleted to undo it, because no Shipment ever referenced them ([`business-workflows.md` §4.4](./business-workflows.md#44-failure-handling)).

- Every entity has `deletedAt`: `null` while the document exists, and the deletion time once it is deleted.
- Services filter out deleted documents explicitly (`{ deletedAt: null }`). There is no middleware that hides them automatically.
- A soft-deleted document keeps its unique values (`id`, codes, email). The same value cannot be reused for a new document.
- Soft delete is separate from `status`. For example, an `INACTIVE` location still exists and can be reactivated.

### Business codes

Human-readable codes are generated by the system, not typed in by users.

| Field | Format | Example |
| --- | --- | --- |
| Item `itemCode` | `T-<nnnn>-<MMYY>` | `T-0001-1026` |
| Shipment `code` | `S-<nnnn>-<MMYY>` | `S-0120-1026` |
| Route `routeNumber` | `R-<nnnn>-<MMYY>` | `R-0007-1026` |
| DockTask `taskNumber` | `<nnnn>-<MMYY>` | `1024-1026` |

- `<nnnn>` is a counter, one per code type, zero-padded to 4 digits. It increases with each new document and restarts at `0001` every month. After `9999` it simply grows to 5 digits (`10000`).
- `<MMYY>` is the two-digit month followed by the two-digit year. October 2026 is `1026`. Because of the month part, codes stay unique even though counters restart.
- The month is determined in Vietnam time (UTC+7), so a document created at 00:30 on 1 November in Vietnam gets a November code.
- Prefixes are upper-case and the format is case-sensitive.
- The schemas validate the format. `formatBusinessCode()` in `backend/src/common/utils/business-code.util.ts` builds a code from its type, counter, and date. The counter is kept in the `metadata` collection (`scope: BUSINESS_CODE_COUNTER`, `key: <TYPE>-<MMYY>`, e.g. `SHIPMENT-1026`) and incremented atomically by `MetadataService.nextBusinessCode()`.
- `barcode` is not a business code. It is the value printed on the item's label and has no fixed format.

### Naming

- Use full `inbound` / `outbound` names. Never abbreviate (`inLegId`, `outLegId`, `inb`, `outb`, ...).
- Shipment code field is `code`, not `shipmentNumber`.
- Enum values are defined once as TypeScript enums/constants and reused; do not scatter string literals.
- Create enums only when the code that needs them is implemented.

## 4. Entities

### 4.1 Location

A physical place: warehouse, cross-dock, store, or customer location. There is **no separate Warehouse collection** in the initial design.

The system manages cross-dock operations at the level of the whole facility. Individual dock doors are **not** modelled: there is no `DOCK` location type and no dock-door entity.

Business roles of the types:

- `STORE`: customer pickup and drop-off locations.
- `CROSS_DOCK`: facilities managed by administrators.
- `WAREHOUSE` and `CUSTOMER`: kept from the original design, not used by any workflow yet.

`STORE` Locations are deduplicated. A new store is reused instead of created when its `name`, `contactName`, and `address.postalCode` all match an existing store, compared case-insensitively after whitespace normalization. A unique index enforces this. See [`business-workflows.md` §2](./business-workflows.md#2-location-reuse-rule).

Content (implemented):

- `id` (ULID). A location has no separate location code.
- `name`
- `type`: `WAREHOUSE`, `CROSS_DOCK`, `STORE`, `CUSTOMER`
- `address`: embedded structured address (`addressLine1` and `postalCode` required; `addressLine2`, `ward`, `district`, `city`, `province`, `country` optional)
- `contactName`, `contactPhone`
- `status`: `ACTIVE`, `INACTIVE` (default `ACTIVE`)
- `metadata`
- `createdAt`, `updatedAt`

### 4.2 User

A system user.

Content (implemented):

- `id` (ULID)
- `fullName`
- `email` (unique, stored lower-cased)
- `passwordHash`, the hash of the password used to log in. Never a plaintext password, and never returned by the API.
- `roles` — one or more of the roles below. A user may hold several. An action is allowed when any of the user's roles allows it.
- `status`: `ACTIVE`, `INACTIVE`, `LOCKED`
- `lastLoginAt`
- `createdAt`, `updatedAt`

Roles (implemented as `UserRole`). The earlier values `OPERATIONS_MANAGER` and `WAREHOUSE_STAFF` are retired and are not kept as aliases.

| Role | May do |
| --- | --- |
| `SYS_ADMIN` | Everything in this table, including creating and editing users and creating Locations. |
| `ADMIN` | Book a shipment and correct a `CREATED` booking (customer name, the two commercial appointments, and the commercial fields of an existing item). |
| `DOCK_MANAGER` | Confirm pickup, confirm delivery, and mark an item missing, once those actions exist ([`scanning-flows.md`](./scanning-flows.md)). |
| `DOCK_OPERATOR` | Scan in and scan out, once those actions exist. |

There is no public registration. A `SYS_ADMIN` creates a user and can later change `fullName`, `email`, `roles`, `status`, and the password. `roles` must contain at least one role. A `SYS_ADMIN` cannot lock their own user or remove `SYS_ADMIN` from their own `roles`. `INACTIVE` and `LOCKED` users do not log in. Soft-deleted users do not log in.

Login (`POST /auth/login`, implemented) checks the email, ignoring case, and the password against its bcrypt hash, and returns a signed JWT. The token carries the user's ULID `id` (`sub`) and their `roles`. It expires 8 hours after it is issued. The client sends it as `Authorization: Bearer`. A wrong email, a wrong password, and an `INACTIVE`, `LOCKED` or soft-deleted user all get the same `401` "Invalid email or password." On a protected endpoint, a missing or invalid token is `401`, and so is a token whose user was locked or deleted after login. A valid token without an allowed role is `403`. The check uses the user's current roles from the database.

Who may call an endpoint that exists today:

| Endpoint | Who |
| --- | --- |
| `POST /auth/login`, `GET /health`, Swagger `/docs` and `/docs-json` | Anyone, no token |
| `GET /locations`, `GET /locations/:id`, `GET /shipments`, `GET /shipments/:id`, `GET /shipments/:id/view` | Anyone, no token, until the frontend has a login screen |
| `POST /locations` | `SYS_ADMIN` |
| `POST /shipments/book` and the three booking `PUT`s | `SYS_ADMIN` or `ADMIN` |
| `POST /users`, `GET /users`, `GET /users/:id`, `PUT /users/:id` | `SYS_ADMIN` |

Dock actions stay unimplemented. When they are added, `performedBy` is the id from the token. Until then, booking still writes the placeholder ULID on a route's `createdBy`.

### 4.3 Item

A real physical item. **The same physical item keeps one stable Item document throughout its whole logistics journey.** Never create a new Item document when the item moves to another shipment segment.

- **Created by its booking:** Items are always created by the booking of a root Shipment, together with it. A booking never reuses an existing Item, and an Item belongs to exactly one root Shipment. A barcode that is already registered is rejected.
- **Kept by routing and by child shipments:** neither step creates or copies Items. Each child shipment references the same Item `id`s. `currentShipmentId` stays the root Shipment until a leg actually carries the item ([`business-workflows.md` §5](./business-workflows.md#5-routing)).
- **At booking:** `status: CREATED`, `currentLocationId` is the pickup Location, and `currentShipmentId` is the root Shipment.

Content (implemented):

- `id` (ULID)
- `itemCode` (unique, `T-<nnnn>-<MMYY>`)
- `barcode` (unique)
- `description`
- `itemUnit`: `BOX`, `PALLET`, `KEG`, `BAG` (required) — the kind of handling unit
- `status`: `CREATED`, `IN_TRANSIT`, `AT_DOCK`, `DELIVERED`, `EXCEPTION`
- `currentLocationId`
- `currentShipmentId`, where applicable
- `weight` with `weightUnit`; `dimensions` (`length`, `width`, `height`, `unit`)
- `metadata`
- `createdAt`, `updatedAt`

The Item stores its current state only. Its movement history comes from DockTask records, not from fields on the Item.

### 4.4 Shipment

A **single** `shipments` collection represents both overall (root) shipments and their segments. Do not create separate `ParentShipment` / `ChildShipment` collections.

A segment (child shipment) is also called a **leg**. Legs are managed as shipments; there is no separate leg entity.

Content (implemented):

- `id` (ULID)
- `code` — the shipment code (not `shipmentNumber`), `S-<nnnn>-<MMYY>`
- `parentId` — ULID `id` of the parent shipment; `null` for a root shipment
- `childrenIds` — ULID `id`s of the child shipments, in path order; `[]` until those children exist
- `customerName` — the customer who booked; required on a root shipment
- `cost` — the booking cost in whole VND, calculated by the system ([`business-workflows.md` §4.3](./business-workflows.md#43-cost)); required on a root shipment
- `itemIds` — ULID `id`s of the Items
- `deliveryInfos` — ordered delivery points (see below)
- `status`: `CREATED`, `IN_TRANSIT`, `AT_DOCK`, `DELIVERED`, `CANCELLED`, `EXCEPTION`
- `metadata`
- `createdAt`, `updatedAt`

Rules:

- `parentId` on each child is the authoritative link. `childrenIds` on the parent lists those same children in path order and must stay equal to them: every id in `childrenIds` has `parentId` equal to this shipment, and every child of this shipment appears in `childrenIds`.
- Do **not** add `originLocationId` or `destinationLocationId`. Pickup, transit, and drop-off information belongs in `deliveryInfos`.
- Every delivery info is connected to a Location through its required `locationId`. The location must exist and must not be deleted.

Each `deliveryInfos` entry contains:

- `sequence` — defines the order of delivery points
- `locationId` — ULID `id` of a Location
- `type` — `PICKUP`, `TRANSIT`, or `DROPOFF`
- `appointment: { from, to }`
- `actualWindow: { from, to }`
- `status`: `PENDING`, `ARRIVED`, `PROCESSING`, `COMPLETED`, `SKIPPED` (same values as route stops)
- `metadata`

### 4.5 Route

An operational route that contains multiple shipment segments and embedded, ordered stops.

Content (implemented):

- `id` (ULID)
- `routeNumber` (unique, `R-<nnnn>-<MMYY>`)
- `shipmentIds` — ULID `id`s of shipment segments
- `stops` — embedded, ordered (see below)
- `status`: `PLANNED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`
- `appointment: { from, to }`
- `actualWindow: { from, to }`
- `createdBy` — User reference (required). Until users exist, booking uses the fixed placeholder ULID `01ARZ3NDEKTSV4RRFFQ69G5FAV`.
- `driverName`, `vehiclePlate` — plain text. Until dispatch exists, every new route uses `Nguyen Van Tai` and `29A-000.01`.
- `items` — snapshot of the items on this route, copied at assignment so a scan does not join Item. It does not include `status` or `currentLocationId`. Scans do not change it. Correcting an Item on a `CREATED` booking rewrites its `description`, `itemUnit`, `weight` and `weightUnit` there.
- `fromLocationId`, `toLocationId` — the two ends. On a dock–dock route they form the lane key together with `serviceDate` (`YYYY-MM-DD`, Vietnam time) and `slot` (`MORNING` or `EVENING`). A store–dock route leaves `serviceDate` and `slot` unset.
- `metadata`
- `createdAt`, `updatedAt`

Rules:

- A shipment segment belongs to one route. A route may carry many segments. The service layer enforces this.
- A store–dock segment gets its own route. A dock–dock segment joins that direction's morning or evening route for the Vietnam calendar day ([`business-workflows.md` §5](./business-workflows.md#5-routing)).
- Every stop is connected to a Location through its required `locationId`. The location must exist and must not be deleted.
- Stops are embedded in the Route document. Do **not** create a separate RouteStop collection.
- Stops and the segments' `deliveryInfos` are kept in sync by explicit service logic, not by schema middleware.

Each stop contains:

- `sequence`
- `locationId`
- `type`: `PICKUP`, `TRANSIT`, `DROPOFF` (same values as delivery infos)
- `shipmentIds` — the segments handled at this stop
- `appointment: { from, to }`
- `actualWindow: { from, to }`
- `status`: `PENDING`, `ARRIVED`, `PROCESSING`, `COMPLETED`, `SKIPPED`

### 4.6 DockTask

One operational action on **one** item. It is not a bulk task containing many items.

Content (implemented):

- `id` (ULID)
- `taskNumber` (unique, `<nnnn>-<MMYY>`)
- `itemId`, `shipmentId`, `routeId`, `locationId` — all required
- `inboundLegId`, `outboundLegId` — legs, i.e. child shipments (`Shipment` references); nullable
- `type`: `SCAN_INBOUND`, `SCAN_OUTBOUND`, `PHOTO`, `INSPECTION`, `EXCEPTION`
- `status`: `PENDING`, `IN_PROGRESS`, `COMPLETED`, `FAILED`, `CANCELLED`
- `performedBy` — User reference; nullable
- `completedAt`; nullable
- `metadata`
- `errorCode`, `errorMessage`
- `createdAt`, `updatedAt`

Which leg references a task type needs is validated in the service layer, not in the schema. Completed tasks form the item's history and must not be overwritten.

Use `inboundLegId` and `outboundLegId`; never `inLegId` / `outLegId`.

## Open questions

Do not invent answers; raise open questions when the related schema or feature is implemented.

Questions 1–27 are resolved and kept here for traceability. Schema-level choices still awaiting confirmation are listed in [`schema-design.md` §10](./schema-design.md#10-decisions-to-confirm).

1. ~~Status values.~~ Resolved: see §4.
2. ~~Location types.~~ Resolved: `WAREHOUSE`, `CROSS_DOCK`, `STORE`, `CUSTOMER`. `DOCK` is dropped because dock doors are not managed (§4.1).
3. ~~Address and contact structure for Location.~~ Resolved: see §4.1.
4. ~~Exact field names.~~ Resolved: see §4.
5. ~~What `inboundLegId` / `outboundLegId` reference.~~ Resolved: a leg is a child shipment, so both reference `Shipment` (§4.4, §4.6).
6. ~~Which leg references each DockTask type requires.~~ Resolved: the per-type rules are enforced in the service layer, not in the schema.
7. ~~Whether `childrenIds` is maintained.~~ Resolved: stored on the parent, in path order, and kept equal to the children found by `parentId` (§4.4).
8. ~~Route stop types.~~ Resolved: same values as delivery info types.
9. ~~Code formats.~~ Resolved: see §3 *Business codes*. `locationCode` was removed.
10. ~~Weight and dimension units.~~ Resolved: `KG` / `LB` and `CM` / `IN`.
11. ~~Deletion policy.~~ Resolved: soft delete for all collections (§3).
12. ~~Shared segments.~~ Resolved: a segment belongs to one route; a route may carry many segments (§4.5).
13. ~~Business code generation details.~~ Resolved: 4-digit zero-padded counter, restarting **monthly** (`MMYY`), chosen over weekly because a calendar month needs no week-numbering rules. The month is taken in Vietnam time (§3 *Business codes*).
14. ~~`AT_DOCK` status name.~~ Resolved: `AT_DOCK` is kept. It means the item or shipment is at a cross-dock or a warehouse.
15. ~~Delivery points and Locations.~~ Resolved: every shipment `deliveryInfos` entry and every route stop has a required `locationId` referencing a Location. Services check that the location exists and is not deleted (§4.4, §4.5).
16. ~~Where the monthly counters are stored.~~ Resolved: a new `metadata` collection is approved (§1). Its documents are identified by `scope` + `key`, and it holds counters and other values or rules that may change. One possible counter entry is `scope: BUSINESS_CODE_COUNTER`, `key: SHIPMENT-1026`. Implemented with shipment creation: `{ id, scope, key, value }`, unique on `scope` + `key`.

17. ~~Location reuse normalization.~~ Resolved: trim, collapse inner whitespace, NFC; case-insensitive comparison through a collation; diacritics significant ([`business-workflows.md` §2](./business-workflows.md#2-location-reuse-rule)).
18. ~~Location reuse scope.~~ Resolved: only `STORE` Locations (customer pickup/drop-off points) are deduplicated, from every source including manual creation. `CROSS_DOCK` Locations are created by administrators for routing and are never deduplicated.
19. ~~Concurrency of find-or-create.~~ Resolved: compound unique index `store_identity` with a case-insensitive collation and the partial filter `{ type: 'STORE', deletedAt: null }`; the service retries the lookup after a duplicate-key error.
20. ~~Roles of `WAREHOUSE` and `CUSTOMER`.~~ Resolved: kept, but not used by any workflow yet.
21. ~~Routing inputs.~~ Resolved: the booking routing step reads the `provinces` collection and each Location's `address.province` ([`business-workflows.md` §5](./business-workflows.md#5-routing)). Postal-code ranges and distances are not used.
22. ~~How a routing result is stored.~~ Resolved: the booking routing step inserts the cross-dock hubs into the root shipment's `deliveryInfos`. The same request then creates one child shipment per hop ([`business-workflows.md` §5](./business-workflows.md#5-routing)).
26. ~~How a child shipment is placed on a route.~~ Resolved: a store–dock child gets its own route; a dock–dock child joins that direction's morning or evening route. `driverName` and `vehiclePlate` are fixed placeholder text until dispatch exists (§4.5). DockTasks are not created at assignment.
27. ~~Who may call the API.~~ Resolved: four roles, a user may hold several, no public registration, token login (§4.2). `GET` reads stay open until the frontend has a login screen. Dock actions are not part of that implementation.
23. ~~Same pickup and drop-off.~~ Resolved: the request is rejected.
24. ~~Appointments at creation.~~ Resolved: pickup and drop-off appointments are supplied when the shipment is created (added to `CreateShipmentDto` with the shipment task).
25. ~~Items in a booking.~~ Resolved: every booking creates new Items with a required `itemUnit` (`BOX`, `PALLET`, `KEG`, `BAG`). Existing Items are never reused for a new shipment; the same Items are used through the shipment's routing and planning.
